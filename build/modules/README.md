# 上游覆盖模块

每个模块把覆盖实现、相关测试、诊断、资源和 `review.json` 放在一起。
构建按阶段调用模块函数，只修改 staging，不改 Desktop、DSH 或插件子模块源码。

## review.json 记录什么

每条记录描述：覆盖原因、关联输入 pin、实现文件、上游目标、调用入口、验证方式和删除条件。
`diagnostics` 列出只在显式调用时运行的模块诊断，不代表打包会自动执行。

- `customization`：产品定制，例如品牌、唯一市场来源；上游升级不意味着应当删除。
- `compatibility`：版本 / 平台适配；上游有等效配置接口后评估缩减。
- `workaround`：临时修复；确认原生行为通过相同回归后才能移除。
- 状态 `active / inactive / upstream` 区分正在应用、尚未接入、上游已接管且这里只验证。

## 升级时怎么检查

完整操作顺序、风险清单与验收边界见 [上游升级检查指南](../../docs/upstream-upgrade.md)。本页只说明覆盖台账。

1. 运行 `yarn product:overlays --check`，按变更的 Desktop、DSH、插件 pin 找到受影响模块。
2. 对照记录检查新上游源码：覆盖目标是否变了，原问题是否已被修复，当前覆盖是否仍接入。
3. 运行 `yarn test:build <模块>`，再执行记录中的 staging / 真机验证。锚点匹配或 pin 未变，不等于行为正确。
4. 如果上游已修复，在独立 staging 中停用对应覆盖，让未经加工的上游通过相同回归，再删除实现及调用；保留必要的行为测试。
5. 验证后人工更新该模块的基线和证据。工具不会自动删除补丁，也不会自动更新基线。

市场服务源码没有独立上游 pin 的记录会明确提示人工复查。局部 Node 测试不替代完整 Market、RPC、许可证、安装与跨平台验收。
本次整理不退役旧覆盖；已有验证缺口保留在各记录中。
