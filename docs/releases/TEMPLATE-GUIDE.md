# 发布说明模板填写规范

完整模板位于 [TEMPLATE.md](TEMPLATE.md)，用于编写面向用户的完整发布说明。分类和中英文组织方式参考 [DeepSeek Harness Releases](https://github.com/deepseek-ai/deepseek-harness/releases)。

## 写作与结构

1. 复制模板到 `v<版本>.md`。首行保留 `# TokensCowork v<版本>`，紧接一两句直接描述功能与修复的中文摘要。摘要供下载页使用，不写发布状态、测试计数或提交 SHA。
2. 保留中文的六个主章节：本次更新、下载说明、安装说明、验证结果、已知限制、完整变更。中英文正文描述相同的功能、限制和验证状态。
3. 更新按“新增功能、问题修复、体验优化、其他变更”分类。没有内容的分类可删除，不为填满模板编造变化。同一变化只写一次。
4. 每条更新说明用户可以做什么、什么场景得到修复或需要调整什么。例如“英文界面下的模型请求失败提示改用英文”，而不是“更新 i18n 提交”。需要注明贡献者时，只使用可核实的 GitHub 用户名或提交关联。
5. 内置组件表从 `product.json` 核对，列出 Desktop / DSH 及实际内置插件；如某项未变化，明确写“沿用”。不要将用户自行安装的插件列为产品内置项。
6. 保留三平台下载链接、校验文件与内置插件清单。支持的最低系统版本、签名和公证状态按实际产物填写，不能从模板直接推断。
7. 安装说明分别覆盖 Windows、macOS 和旧版本升级。没有迁移要求时明确写“无需迁移”；数据保留和重新授权要求应有实现或验收依据。
8. 验证结果区分构建、自动测试、真机安装与人工验收。没有执行的检查写“未验证”；仍在运行的写“进行中”。CI 构建成功不等于真机安装或功能验收成功。
9. 已知限制写明具体影响及已确认的临时处理办法；没有已知问题时写明当前验证范围，不作无依据保证。不要把已修复问题重复放入限制。
10. 完整变更链接必须对应实际起止标签。源码 SHA、测试数量和工作流链接放在验证章节，避免挤占用户更新条目。

## 当前实现边界

- 构建和晋级使用 `--format full`：要求六个中文及六个英文主章节按顺序出现、至少一个对应的更新分类、当前版本下载链接、安装升级子章节及内置组件信息。空章节和占位符不能发布；没有内容的更新分类仍可删除。
- 发布脚本读取填写完成的版本 Markdown 并附加发行类型标记，不会自动补写未经验证的功能或验收结果。
- 下载页按所选语言展示说明，以版本号排序，正式/预发布状态仍取自 GitHub 元数据。旧单语说明保持可读。

## 预发布与正式发布

- 新构建一律生成预发布；说明描述相对上一个候选版本的增量变化，状态在 GitHub 元数据中管理。
- 正式发布使用 `Promote Desktop Release` 工作流，输入已有的 `vX.Y.Z` 标签。它验证三平台安装包、校验文件和插件清单存在，复用既有标签与附件，不重新构建、不修改版本号。
- 晋级前将该版本 Markdown 更新为完整的双语说明，汇总上一正式版以来的用户可见变化。两种语言的完整变更链接均须以该正式版为起点；不能仅把最后一轮预发布的说明直接当作整个正式版的说明。
- 晋级脚本拒绝草稿、已正式发布的版本、低于最新正式版的版本和缺少附件的版本。没有上一正式版时按首次正式发布处理。
- 下载页的升级摘要按版本号汇集两个正式版之间的各版摘要；候选说明应避免发布状态和重复套话。保留规则仅用于 `v0.4.0` 之前的历史版本，因此不会删掉当前系列的摘要来源。

## 语言导航

GitHub Release 不会为 Markdown 标题生成自动锚点。保留模板中的两个 `<a name="release-notes-zh/en"></a>` 及对应的 `#user-content-release-notes-zh/en` 链接；GitHub 会为 name 添加 `user-content-` 前缀。链接跳转到对应语言段落；下载页的中文 / EN 按钮则只显示所选语言。
